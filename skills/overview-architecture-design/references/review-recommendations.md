# 标准架构设计目录评审与补充建议

## 1. 总体结论

你给出的 20 项已经覆盖了系统架构的主要视图，作为中小型项目的基础目录是合格的；但要作为组织级、金融级、高并发或信创项目的标准模板，还需要做两类增强：

1. 补齐“架构原则、质量属性、领域架构、文档治理、架构决策”；
2. 明确架构设计与详细设计、测试设计、项目管理之间的边界。

建议结论：**pass_with_followups**。本目录已按“概要架构设计 → 详细设计 → 测试设计/开发”拆分，适合作为团队级标准模板。

## 2. 现有目录的优点

- 全链路视角完整：周边系统、内部模块、数据、技术、部署都有覆盖。
- 已单列安全、可观测、灾备、迁移、发布、容量等容易遗漏的内容。
- 兼顾技术架构和项目落地，成本、资源、进度约束也被纳入。
- 能覆盖高并发、金融、信创和多租户场景的主要评审维度。

## 3. 需要补充的关键内容

### P0：架构原则与质量属性

当前目录直接进入项目概述和架构视图，缺少“为什么这样设计”的统一判断标准。

建议新增：

- 架构原则；
- 业务约束与技术约束；
- 性能、可用性、安全、可恢复性等质量属性场景；
- 每个质量属性对应的数值指标和验证方法。

“高性能”“高可用”必须改写成 P95、QPS、SLA、RPO、RTO、恢复时间等可验收指标。

### P0：文档治理与评审状态

建议增加文档控制页：

- 文档版本、作者、Owner；
- 评审人和评审结论；
- 变更记录；
- 未决问题；
- 架构有效期；
- 关联需求、设计、API diff、测试和运维文档。

否则架构文档很容易在上线后失效且无人维护。

### P1：领域/业务架构

现有目录从整体架构直接跳到逻辑架构，缺少业务能力与领域边界。

建议增加：

- 业务能力地图；
- 核心域、支撑域、通用域；
- 领域实体、聚合和数据所有权；
- 领域事件和上下文映射；
- 领域边界与组织边界。

### P1：接口与事件契约

“接口设计”建议拆成：

- 外部 HTTP API；
- 内部 RPC/Interface；
- MQ/事件；
- 文件导入导出；
- 错误码和响应包装；
- 幂等键；
- 超时、重试、熔断和降级；
- 版本兼容和弃用策略。

对于新增或修改的外部契约，应同步产出 OpenAPI、AsyncAPI 或 api-diff.yaml。

### P1：数据治理生命周期

数据架构不应只停留在 ER 图和数据流，还应覆盖：

- 数据分类分级；
- 数据所有权；
- 数据质量；
- 数据血缘；
- 热冷分层；
- 归档与清理；
- 备份恢复；
- 脱敏与访问审计；
- Schema 演进。

### P1：部署架构与运行架构分离

部署架构不仅是节点和网络拓扑，还需补充：

- 故障域/AZ/机房；
- 弹性伸缩；
- 健康检查；
- 自愈；
- 连接池和线程池；
- 队列积压；
- 灰度流量；
- 运维入口和管理面隔离。

### P1：架构决策与技术债

建议显式维护 ADR：

- 背景；
- 决策；
- 备选方案；
- 取舍；
- 影响；
- 回滚/替代条件；
- Owner 和复审时间。

技术债不能只写“后续优化”，必须有触发条件、Owner 和期限。

## 5. 需要标记“必填/条件必填/可下沉”的章节

| 章节 | 默认级别 | 说明 |
|---|---|---|
| 项目概述、整体、逻辑、数据、技术、部署 | 必填 | 所有项目必须有 |
| 安全架构 | 必填 | 即使是内部系统也要说明认证、授权和敏感数据 |
| 可观测性 | 必填 | 至少定义日志、指标、告警和 requestId |
| 核心逻辑 | 必填 | 核心流程应有时序图/状态机 |
| 接口与事件契约 | 有接口则必填 | 没有外部接口也要说明内部边界 |
| 容灾 | 生产系统必填 | 非生产项目可写适用性结论 |
| 数据迁移 | 有历史数据/改表则必填 | 无迁移需明确写不适用 |
| 发布策略 | 生产系统必填 | 至少有灰度、回滚和观察窗口 |
| 成本预算 | 资源型/云项目必填 | 内部小工具可简化 |
| 测试策略 | 架构验证必填 | 详细测试用例下沉到测试设计 |

## 6. 架构设计与其他设计阶段的边界

| 内容 | 架构设计 | 详细设计 | 测试设计 |
|---|---|---|---|
| 模块职责 | 必须 | 细化类和方法 | 验证边界 |
| 表结构 | 核心实体和所有权 | 字段、索引、DDL | 数据构造 |
| API | 风格、边界、版本 | 字段级契约 | 契约测试 |
| 性能 | 目标和容量模型 | SQL/缓存优化 | 压测用例 |
| 安全 | 信任边界和原则 | 过滤器、策略实现 | 渗透/安全用例 |
| 灾备 | RPO/RTO和策略 | 切换步骤 | 恢复演练 |

## 7. 常见质量门禁

提交架构设计前至少检查：

- 是否明确系统边界和数据所有权；
- 是否有架构上下文图、逻辑图、部署图；
- 是否所有 NFR 都有数字目标；
- 是否区分同步接口和异步事件；
- 是否说明超时、重试、幂等、熔断、降级；
- 是否定义认证、授权、加密、脱敏、审计；
- 是否定义日志、指标、告警、Trace；
- 是否定义 RPO/RTO 和恢复演练；
- 是否有发布、回滚和迁移策略；
- 是否有 ADR、风险 Owner 和未决问题；
- 是否能进入详细设计而不依赖口头补充。

## 8. 最终建议

你的原始目录不是缺少“章节数量”，而是缺少“架构决策闭环”。建议采用：

- 23 章标准模板作为组织级模板；
- 20 章简化模板作为中小型项目模板；
- 章节级别标记必填/条件必填；
- 所有架构结论必须对应指标、图表、Owner 或验证方式；
- 复杂接口、表结构和测试用例分别下沉到详细设计和测试设计。

## 9. 概要架构与详细设计的分工

### 9.1 概要架构设计

重点回答：系统为什么建设、边界在哪里、由哪些能力和模块组成、如何满足质量属性、关键取舍是什么。

建议包含：项目目标与边界、业务能力、系统上下文、领域边界、逻辑模块、数据流、技术选型、部署拓扑、安全/可观测/容灾总体策略、质量指标、ADR、风险和演进路线。

不建议展开数据库字段、索引、DTO 字段、类方法、SQL 和逐步骤异常分支。

### 9.2 详细设计

重点回答：模块如何实现、接口和事件字段是什么、数据表如何落地、流程如何执行、异常如何处理、如何迁移和验证。

建议包含：模块/类设计、HTTP/RPC/MQ/文件契约、API diff、表结构和索引、缓存、时序图、状态机、事务、幂等、并发、补偿、安全实现、日志指标、资源规格、发布回滚和测试验证。

### 9.3 两阶段关联规则

1. 使用“需求编号 + 模块编号 + API/事件编号 + ADR 编号”建立追溯关系。
2. 概要架构未达到 `approved` 时，详细设计只能处于草稿或并行评审状态。
3. 详细设计若改变系统边界、核心技术选型或一致性模型，必须回写概要架构并新增 ADR。
4. 外部 HTTP、RPC、事件或文件契约发生变化时，必须同步维护 API diff。
5. 详细设计完成后进入测试设计，不能用架构文档替代测试用例和验收标准。

### 9.4 三项执行级强化规则

- 详细设计正文必须执行“变更回写检查”；若改变系统边界、核心技术选型或一致性模型，先更新概要架构并新增 ADR。
- 概要架构中的每个质量属性目标必须填写“基线来源”，从历史监控数据、压测报告、业务 SLA 协议、行业基准或容量模型推算中选择。
- API-Diff 统一按 `api-diffs/{模块编号}/{API编号}_v{版本号}_diff.yaml` 存放和命名，保证契约可追溯。
