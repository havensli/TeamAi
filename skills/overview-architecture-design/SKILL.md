# 概要架构设计

## 目标

产出可评审、可追溯、可进入详细设计的概要架构文档。回答“为什么这样设计”和“系统由什么组成”，不替代字段级接口、表结构或类级详细设计。

## 必读资源

1. 读取 `references/overview-template.md`，按其章节组织输出。
2. 需要判断准入或裁剪章节时读取 `references/review-recommendations.md`。
3. 若仓库存在 `AGENTS.md`、`specs/AGENTS.md` 或设计规范，先遵循仓库规范；用户要求优先于模板默认值。

## 工作流

### 1. 识别输入和范围

- 收集需求、业务目标、现有系统约束、上下游依赖、非功能指标和合规要求。
- 明确 `In Scope`、`Out of Scope`、系统边界、数据所有权、租户/组织/地域边界。
- 对棕地系统标记复用、扩展、替换和新增点，不臆造现有能力。
- 缺失信息写入 `assumptions` 和 `open_questions`，不要将假设写成已确认事实。

### 2. 形成架构视图

至少输出：业务能力地图、系统上下文图、领域/上下文映射、逻辑模块图、核心数据流、技术栈表、部署/故障域拓扑。复杂关系优先用 Mermaid 表达，并附文字说明。

### 3. 固化横切设计

- 安全：认证、授权、信任边界、加密、脱敏、审计和合规责任。
- 可观测性：日志、指标、告警、Trace、requestId/traceId 传播和 Runbook 责任。
- 高可用/容灾：故障模型、SLA/SLO、RPO/RTO、自愈、备份和演练频率。
- 容量：QPS/TPS、P95/P99、并发、数据增长、扩缩容指标和资源假设。

### 4. 量化质量属性

质量属性表必须包含“指标/目标值、基线来源、验证方式”。基线来源只能从以下值选择并说明证据：历史监控数据、压测报告、业务 SLA 协议、行业基准、容量模型推算。

### 5. 记录决策与风险

每个关键取舍记录备选方案、原因、影响、复审条件和 Owner；用 ADR 索引关联详细决策。风险必须包含概率/影响、触发条件、应对和 Owner。技术债必须有期限或触发条件。

### 6. 输出和准入

文档末尾强制输出：

- `status`: `pass` / `pass_with_followups` / `blocked`
- `assumptions`
- `open_questions`
- `risks`
- `next_step`

只有系统边界、模块职责、数据所有权、质量指标、安全/可观测性责任、关键 ADR 和详细设计范围明确后，才建议将概要设计标为 `approved`。外部契约只描述风格、边界和版本；字段级契约下沉到详细设计并生成 API-Diff。

## 禁止越界

不要在概要设计中伪造数据库字段、索引、DTO 字段、类方法、SQL、逐步骤异常分支或测试用例。若这些内容决定架构方向，只描述约束和决策，并在 `open_questions` 中列出详细设计待确认项。

## 交付物

- 概要架构设计 Markdown 文档；
- Mermaid 图表或图表索引；
- ADR 索引、风险清单和开放问题；
- 详细设计准入清单；
- 若用户要求，可创建 `adr/ADR-xxx.md`，但不要未经授权修改代码。
